# 本地操作手册

## 准备环境

在解压目录的包根运行以下命令。后续示例以 `python -X utf8 scripts/workbench.py` 为前缀。使用包内入口可自动找到知识库和状态数据库。

```powershell
python -X utf8 scripts/workbench.py doctor
python -X utf8 scripts/workbench.py vault verify
python -X utf8 scripts/workbench.py vault search "采购角色" --scope methods
```

Obsidian 检测覆盖 Windows 安装登记和常见位置、macOS 应用目录、Linux 的 PATH 和常用发行形式。自定义目录可用 `doctor --obsidian-executable "<绝对路径>"`。检测不到时从 [官方下载页](https://obsidian.md/download) 安装，然后在仓库管理器打开 `vault/`。处理 Markdown 可直接使用本地文本工具。Obsidian 应用安装由用户按官方流程完成。

## 用已有知识生成新仓库

将 [知识库生成提示词](知识库生成提示词.md) 与市场、产品、买家资料交给模型。输出 JSON 时可用包内十张 [示例卡](../examples/method-cards.zh-CN.json) 验证格式。

```powershell
python -X utf8 scripts/workbench.py knowledge new --dest "./example-b2b-vault" --name "领英B2B方法库"
python -X utf8 scripts/workbench.py knowledge load --vault "./example-b2b-vault" --cards "<模型生成的 JSON 文件>"
python -X utf8 scripts/workbench.py vault --vault "./example-b2b-vault" index
```

给包内库增加方法卡时，把 --vault 指向包根的 `vault`，导入后运行 `vault index`。原库的历史资料、带出处的本地归纳和模型通用方法分别存放。检查历史笔记时从本业务的原始记录核对范围。运行 `vault verify` 检查可核验的本地引用与索引。

## 接入旧历史

导入和写稿使用同一个 `--state` 目录。省略时程序按所在系统选用户数据目录。台账保存数据库里的独立记录，现有表格仍可继续作为业务资料使用。

```powershell
python -X utf8 scripts/legacy-history.py "./your-customer-history.json" --out "./legacy-import.csv" --review "./legacy-review.json"
python -X utf8 scripts/workbench.py ledger import-history "./legacy-import.csv"
python -X utf8 scripts/workbench.py ledger report
```

旧记录保留研究、已写草稿、联系过、未决和停联。日期或渠道从来历判断不出时留空或保留待核渠道。复核文件列出缺国家或身份信息的行。转换不会把导入自动记成完整覆盖。Excel 等其他格式可另导出 UTF-8 CSV，参考以下字段。

```csv
name,country,domain,registration,aliases,channel,state,source,coverage
Example Shop,GB,example.test,,Example Trade,email,researched,示例工作簿行号,
```

国家用两字代码，例 GB 或 US。别名用竖线连接。已明确证实检查范围时使用 `history-review` 标明渠道和范围，考虑既有台账、邮箱、网站表单、领英与其他曾使用的渠道。未知国家 ZZ 与缺渠道都要先补证据。确证国家后，可用 `ledger verify-country --company <原ID> --country GB --source "<主体证据>"` 保留原编号与历史。有身份冲突时进入待核。导入报出身份冲突时先核对公司主体再重试整批。对于绝对无关的业务，使用同工作台不同的 `--state`，保留各自边界。

## 从研究到草稿

1. 读知识库当前索引，记录目标市场、买家画像、产品证据。
2. 用 `ledger company --name "Example Shop" --country GB --domain example.test` 建立或定位公司 ID，再用 `ledger status --company <公司ID>` 读历史。
3. 按实际核查写 `ledger history-review --company <公司ID> --channel email --coverage checked --source "<核查日期、账号与范围>"`。检查只覆盖部分时填 `partial`，将未决项放入研究队列。用 `ledger gate --company <公司ID> --channel linkedin --kind first-contact --required-channel email` 查看跨渠道重复、停联和证据缺口；若发现旧接触，按真实上下文保留为跟进对象或停联。
4. 将英文稿、中文审阅稿保存为普通 UTF-8 文件。草稿录入保留准确渠道、目标及证据。有缺口的线索也可研究并保存内部草稿，其状态单独判断。命令示例见下。
5. 内容稿使用 `--kind content`，提供素材或事实依据。近似提醒比较台账已有稿件，另外阅读打包库最近运营记录的历史帖子主题。已有帖子确切正文可登记为带原帖链接的参考内容。业务角度相同或仅换措辞时重写。

```text
ledger draft --id draft-001 --kind first-contact --company <公司ID> --channel linkedin --target "<已核对的对象>" --subject "<简短标题>" --body-file "./first.en.txt" --review-file "./first.zh.txt" --evidence "<真实资料引用>"
ledger show-draft --id draft-001 --show-body
ledger draft --id post-001 --kind content --channel linkedin --subject "<选题>" --body-file "./post.en.txt" --review-file "./post.zh.txt" --evidence "<事实或素材依据>"
```

## 运行窗口和任务

```text
session start --goal "研究目标客户并准备双语稿" --scope "英国园艺与家居零售" --duration 2h
session add <run_id> --kind research --title "核对潜客主体及跨渠道历史" --priority 80 --key research-001
session add <run_id> --kind content --title "准备与近期内容不同的买家问题" --priority 60 --key content-001
session next <run_id>
session claim <run_id>
session done <run_id> <task_id> --result "<实际交付物或核验证据>" --worked-seconds <实测秒数>
session switch <run_id> <task_id> --reason "<实际阻塞原因>" --waiting
session resume <run_id> --reason "<重启后恢复>"
session report <run_id> --events
session close <run_id> --reason "<原因>" --events
```

按实际工作顺序领取任务，受阻可切换其它待办。switch 输出中的 next.task 为下一项已领取任务。不填时长就没有截止，队列完成或无可执行任务时据实结束。恢复时使用同一数据库与 run_id。未知中断先查产物，用 `done` 结算，或凭对账依据执行 `requeue … --reconciled`。截止后只收集在途结果。未量度的工作区间如实保留为未计量。计划时间、工作、等待或阻塞各自统计。

## 执行与回执

销售经理的公司主页、公开互动、群组研究以及领英控件核对，见[销售经理领英实操手册](销售经理领英实操手册.md)。

领英动作分别使用 `content`（发帖）、`first-contact` / `follow-up`（私信）、`comment`（评论）、`connection-invite`（连接邀请）和 `group-join`（入群申请）。评论、邀请、入群申请各提供准确的领英帖子、人物或群组链接及核验依据。入群申请的草稿文件保存申请理由及必答问题。

```text
ledger draft --id comment-001 --kind comment --channel linkedin --target "<已核验的领英帖子 URL>" --subject "<原帖标题>" --body-file "./comment.en.txt" --review-file "./comment.zh.txt" --evidence "<原帖或核验证据>"
```

这些动作沿用下方的版本批准、动作意图和回执。申请待审时记为申请已提交，将状态留在回执证据；看到平台成员状态再记录已入群。按动作分类统计结果，私信的公司联系数与评论、邀请和入群分开。

经用户确认实际渠道、对象及精确内容后，才能使用 `ledger approve` 登记该版，`ledger intent` 创建以稳定 key 为索引的一次意图。程序是本地记录器。发布可使用 [领英原生排期](https://www.linkedin.com/help/linkedin/answer/a1347212) 或已连通且拥有对应权限的发布工具。消息与邀请需另有相应渠道。收到真实回执后，以准确消息或帖子 ID 与有时区时间入库。

```text
ledger approve --id <草稿ID> --version <精确版本> --by "<审阅人>"
ledger intent --id <草稿ID> --version <精确版本> --key <稳定动作键> --account "<确切账号标识>" --required-channel email
ledger receipt --key <稳定动作键> --result unknown --source manual --evidence "<已观察到的失败或超时>"
ledger action --key <稳定动作键>
ledger receipt --key <稳定动作键> --result confirmed --source manual --evidence "<已核对回执说明>" --external-id "<确切消息或帖子 ID>" --occurred-at "<含时区的实际时间>"
```

重复调用意图只查到原记录。首次返回的 pending 代表登记完成。结果不明确先处理既有动作，明确未执行后记 `not-executed`，按本轮授权决定能否重新安排。记录业务回复、确认需求、样品、报价、订单时使用 `ledger milestone`，填实际对话证据与确认事项。个人连接、评论、礼貌问候和未获回复保持原状态。内容排期、内容发布与确认回执各按实际状态记录。

## 复盘

利用 `ledger snapshot` 按帖子与采集时间记录曝光、触达和互动。未检查时省略相应指标，界面明确未展示时使用 `--impressions-state not-displayed`（reach、interactions 同理），显示为零时传数字 0。用 `ledger snapshots --post <帖子ID>` 查看同帖多次读数，用 `ledger report` 看最新快照和唯一公司事件。把 `session report` 的任务时间与业务行动统计联合使用，分开写出研究、草稿、实际发布或联系、有效对话、明确需求和下一步。

每轮优先保存尚缺证据与到期事项。看同一首触批次与同一观察窗口，一次改一个可比较变量。原始记录中出现的发布、消息、邀请、点赞及浏览数据可以帮助复盘，实际发生的业务变化以已保存的事件与证据为准。
